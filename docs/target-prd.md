# Peak Trekker To-Be PRD v0.2

## 1. 产品定位

Peak Trekker 是一个面向登山 / 徒步场景的移动优先产品：

* 先帮助用户**找到值得去的山**
* 再通过 **GPS、照片补签，及后续可扩展的结果导入方式** 留下一次真实山行
* 最后把这次山行沉淀成 **个人活动、可传播素材、山友圈内容、所属省份的长期归属贡献**

一句话定义：

> **一个以山为锚点、以单次真实山行为核心对象、以海拔与登顶证据为信任符号、以分享和回看为长期价值的登山产品。**

### 1.1 我们是谁

Peak Trekker 不是重地图导航工具，不是泛社交社区，也不是单纯的海报生成器。  
它要做的是：

* 帮用户更快找到一座适合自己、值得去的山
* 帮用户把一次真实山行可信地留下来
* 帮用户把这次山行整理成好看、可回看、可分享的个人资产

### 1.2 我们不靠什么竞争

我们当前不依赖以下能力作为主定位：

* 专业级重地图导航
* 大规模 UGC 路线地图生态
* 组队 / 备赛工具链
* 泛内容社交广场
* 复杂训练分析和专业图表系统

### 1.3 我们的核心差异化方向

1. **找山更顺**
2. **接入更宽**
3. **记录更真**
4. **海拔被看见**
5. **分享更美**
6. **回看更有意义**

## 2. 产品阶段目标

### 2.1 当前阶段核心目标

第一，建立稳定的 **找山 → 决策 → 记录 / 留证 → 活动沉淀** 主链路。  
第二，让产品不仅能服务“从山脚开始记录”的用户，也能接住“结果现在才被带回来”的用户。  
第三，把“单次真实山行”做成独立、完整、可信、易回看的核心对象。  
第四，让海拔、登顶与关键证据在找山、记录、分享、回看四段里都被优先看见。  
第五，强化分享素材系统，让用户每次有效山行都能快速产出可传播内容。  
第六，山友圈继续只做真实活动驱动的信息流，不做泛社交广场。  
第七，省域热力继续只做轻量归属机制，不做复杂竞技。  
第八，上线前必须同步完成主线可信度、关键物料、文案体验、FAQ、轻量地图 / 天气方案的收口。

### 2.2 当前阶段明确不做

不做收藏 / 想去体系。  
不做重地图导航能力。  
不做专业向导式路线建议。  
不做完整备赛工具链。  
不做重成就墙。  
不做复杂省域竞技系统。  
不做与登山弱相关的泛内容社交。  
不把分享系统做成专业图表工具或复杂模板编辑器。

### 2.3 当前阶段必须补齐但不走重投入的能力

虽然当前阶段明确不做重地图导航和专业天气服务，但**上线前必须补齐轻量地图参考能力与轻量天气接口方案**，用于：

* Mountain Detail 决策辅助
* Trek 轻量辅助
* 分享素材辅助
* FAQ 和用户说明中的明确预期管理

## 3. 核心设计原则

### 3.1 主语优先

产品的核心对象是“**我的一次真实山行**”，不是山本身，也不是帖子本身。

### 3.2 决策优先

Explore 负责找山，Mountain Detail 负责出发决策。  
首页不再只服务找山，但找山仍是最重要的主路径之一。

### 3.3 真实优先

所有公开内容、热力贡献、可传播活动，都应尽量建立在有效记录或有效证据之上，弱化“空发帖”。

### 3.4 接入更宽

产品不能只服务“全程都在 Peak Trekker 里完成记录”的用户，也要接住以下真实场景：

* 到山顶才想起来打开
* 用别的设备记录完，再回来整理
* 先有照片，再做留证
* 先有结果，再补记录

### 3.5 海拔被看见

海拔不是普通字段，而是 Peak Trekker 的高优先级产品信号。  
它既代表目标感，也代表过程感，更代表结果证明。

### 3.6 简洁传播

分享系统提供有限但关键的选择权，不演化成复杂编辑器。  
重点是“快、好看、好传播”，而不是“功能越多越专业”。

### 3.7 移动优先

所有关键页面默认以手机端体验为基准设计，特别是操作区、弹窗、底部按钮区和固定 CTA。

### 3.8 通用操作 icon 化

关闭、分享、编辑、返回、更多、删除、下载、举报等高频动作，优先用 icon button，不再优先用纯文字操作。

## 4. 信息架构

## 4.1 一级模块

### 首页 / 意图分流

首页不应长期只等于 Explore，而应逐步承担**意图分流**职责，优先帮助用户判断这次进入产品是为了：

* 去找下一座山
* 把这次结果带回来
* 回看自己已有的山行资产
*首页意图分流是已确定的战略方向；
*本次上线前只要求文档与信息架构对齐，正式产品落地归入 P1。

### Explore

找山、筛选、进入山峰详情。  
这是“下一座山去哪”的主入口。

### Mountain Detail

围绕一座山的决策页。  
负责帮助用户判断这座山值不值得去、能不能去、该怎么理解路线与条件。

### Record / Activity

开始记录、照片补签、活动详情、结果沉淀、素材生成。  
这是核心资产层。

### Community

基于真实活动生成的公开内容流。  
这是表达层，不是产品中心。

### Profile

用户身份、头像、执照、我的记录、我的分享、省份归属。  
它既承担身份表达，也承担长期回看。

### Province Heat

轻量月榜与省域贡献模块，可挂在 Profile 或相对独立的入口中。  
它服务于归属感，不服务于复杂竞技。

### FAQ / 使用说明

面向上线后的用户教育、预期管理和常见问题说明。  
这是正式产品的一部分，不是临时补丁页。

### Admin / QA / 内部工具

后台治理、审核、物料维护、精选内容运营、山峰数据维护、点位编辑、回归验收工具。  
这些不属于普通用户主流程，但属于当前项目有效范围。

## 5. 关键用户流程

## 5.1 新用户流程

进入产品后，先完成轻 onboarding。  
然后选择所属省份，建立省域身份锚点。  
接着进入首页意图分流或 Explore，浏览山峰列表，点进一座山的详情页。  
在详情页看完核心信息后，决定是否开始记录。  
记录完成后，沉淀成活动对象，再决定是否分享、是否发山友圈。

### 新用户目标

* 知道先去哪
* 理解产品不是泛社交，而是围绕真实山行
* 在第一次成功记录后建立“记录 → 活动 → 分享 / 发布”的闭环心智

## 5.2 老用户流程

老用户通常有三种进入方式：

* 继续找下一座山
* 把刚完成的一次山行结果带回来
* 回看自己已有的山行资产

首页应逐步从“纯找山入口”演进为“意图分流入口”；Explore 仍是一号找山路径，但不再独占首页逻辑。

## 5.3 结果带回型流程

对于真实徒步场景，用户并不一定从山脚就打开 Peak Trekker。  
因此产品要能接住这些情况：

* 到山顶才打开
* 行程结束后才整理照片
* 之前在别的平台 / 设备上记录，回来补结果
* 只想保留一次登顶留证，而不一定有完整过程

当前阶段要先在产品定义和记录分层上为这些场景留入口；后续阶段再扩展更完整的导入与自动核验能力。

## 6. 模块定义

# 6.1 首页 / 意图分流

## 目标

帮助用户判断本次进入产品的真实意图，而不是默认所有用户都先去找山。

## 核心职责

* 引导去找下一座山
* 引导把这次结果带回来
* 引导回看已有山行

## 原则

* 不做社交流首页
* 不做复杂 dashboard
* 不堆叠过多入口
* 不抢 Explore 的找山职责
* 不让 Community 抢占首页主叙事

---

# 6.2 Explore：找山页

## 目标

快速帮助用户决定“下一座山去哪”。

## 页面结构

顶部搜索框。  
快捷筛选区。  
山峰列表卡片流。

## 卡片固定信息

山峰主图。  
山峰名。  
地点。  
海拔。  
预计距离 / 时长。  
难度等级。  
执照要求。

## 不包含

不做收藏。  
不做想去。  
不做过多弱相关标签。  
不承担结果带回和回看资产的全部入口职责。

## 标签规则

沿用现有执照 / 难度体系，不再额外造一套兴趣标签体系。

## 核心判断

Explore 很重要，但不再等于产品唯一首页逻辑。  
它的职责是**找山**，不是承接所有回访流量。

---

# 6.3 Mountain Detail：山峰详情页

## 目标

帮助用户判断这座山值不值得去、能不能去、该怎么理解这条路线。

## 页面结构

### A. 首屏视觉区

主图轮播。  
返回、分享、更多。  
主 CTA：开始记录。

### B. 核心概览区

山峰名。  
地点。  
海拔。  
距离。  
爬升。  
预计时长。  
难度等级。  
执照要求。  
适合人群等级。

### C. 山峰简介区

基础简介。  
经典打卡点说明。  
拍照价值点说明。  
山峰的独特气质和适合人群判断。

### D. 关键点位 / 参考路线区

静态路线参考图。  
简要路线说明。  
关键点位说明（如景观点、补给点、折返点、风险点）。  
风险提示：

> 本路线仅供参考，实际请结合现场情况、天气、专业地图、向导与自身能力综合判断。

### E. 天气区

轻量天气信息展示，不做专业预测承诺。

### F. 精选攻略 / 山友经验区

来源仅限已发布山友圈内容。  
需要后台人工精选。  
按时间由近到远排序。  
没有内容时整个模块隐藏。

## 关键原则

* Mountain Detail 是决策页，不是信息堆砌页
* 地图只做静态参考，不做专业导航
* 天气只做轻量提示，不做专业天气承诺
* 攻略区是“帮助判断”的内容，不是普通评论区
* 无精选内容时不强行留空模块

# 6.4 Record：单次真实山行

## 目标

把一次登山行为沉淀成完整对象，而不是社区附属物。

## 产品定义

单次山行是独立于山友圈内容的第一对象。

### 活动记录包含

用户是谁。  
发生时间。  
目标山峰。  
地点 / 海拔。  
是否登顶。  
距离 / 爬升 / 时长。  
轨迹。  
照片。  
备注。  
分享素材。  
公开状态与留证状态。

### 活动记录与山友圈关系

活动记录可以不发山友圈。  
山友圈内容必须基于活动记录生成。  
删除山友圈内容，不影响活动记录本身保留。

## 记录方式

实时 GPS 记录。  
照片补签记录。  
后续可扩展的轨迹导入 / 结果补录能力。

### 记录前置规则

必须先确定目标山峰。  
未确认目标山峰不得开始正式记录。  
高等级山峰对低等级用户不开放。

### 有效性规则

沿用当前有效记录门槛、峰顶接近判断、短记录无效、漂移过滤等机制。  
这部分在正式 PRD 中视为安全和真实性边界，不因为想提高接入率而放弃真实性原则。

### 记录分层

#### 完整山行

过程证据较完整，适合成为最完整、最可信、最适合公开传播的记录类型。

#### 登顶留证

过程不一定完整，但到达结果有明确证据。  
适用于“到顶才打开”“只有到顶素材”“后补结果”的场景。

#### 个人归档

更偏私人记忆留存。  
可以保留记忆价值，但不一定自动获得全部公开资格。

### 分层目标

这个分层的目的不是抬高门槛，而是：

* 不把真实用户挡在门外
* 不把所有记录混成同一可信等级
* 为未来导入轨迹、补签、审核和公开资格打基础

# 6.5 活动详情页

## 目标

让用户回看一次完整山行，并进行二次分享或发布。

## 页面结构

顶部封面区。  
活动标题。  
日期。  
山峰名。  
地点 / 海拔。  
是否登顶。  
核心数据区。  
轨迹图。  
照片区。  
路线关联区。  
分享入口。  
发布山友圈入口。  
备注 / 感受 / 记忆锚点区。

## 封面规则

优先用户照片。  
无照片则使用自动生成的活动结果图。  
仍无可用图时，用山峰默认图 + 活动数据叠层。  
禁止出现大面积空白封面。

## 方向定义

活动详情页不仅是“记录详情页”，也是一次山行的回看对象。  
它应优先帮助用户保留少而精的记忆锚点，而不是堆叠所有过程信息。

# 6.6 分享素材系统

## 目标

把一次真实山行快速转化成可传播内容。

## 战略定位

这是核心功能，不是实验功能。  
它是活动结果的表达层，不是专业图表工具或模板编辑器。

## 模板体系

### 默认结果卡

自动生成。  
包含轨迹和核心数据。  
适合最快传播。

### 照片合成卡

用户照片 + 活动数据。  
适合图文传播。

### 透明水印层

适合用户拿去二次加工，特别是视频场景。

## 编辑边界

当前阶段允许的选择权最多做到三层：

* 选模板
* 选主图 / 背景
* 选展示哪些字段

当前阶段明确不做：

* 复杂拖拽排版
* 大量专业分析图表
* 模板商城式扩张
* 训练分析型图层

## 内容优先级

素材中优先显示：

* 山峰名
* 时间
* 海拔
* 是否登顶
* 距离
* 爬升
* 时长
* 轨迹

## 视觉原则

向 Strava 式简洁表达靠近。  
优先干净、数据明确、轨迹清楚。  
不做复杂地形剖面图。  
不做过度装饰。  
不做厚重大海报感。

---

# 6.7 Community：山友圈

## 目标

做真实活动驱动的信息流，而不是泛社交广场。

## 内容来源

只能来自有效活动记录。  
公开内容与活动对象强绑定。  
用户只补充表达层，系统数据不可随意改写。

## Feed 卡片固定结构

用户信息。  
活动标题。  
时间。  
地点。  
山峰。  
是否登顶。  
核心数据。  
默认轨迹 / 路线图。  
用户照片 / 视频。  
摘要。  
分享、点赞、评论、更多。

## 关键改造点

发布链路前置。  
用户在活动页或分享页产出素材后，应可快速发布到山友圈。  
减少绕路，不再把“发布”藏得太深。

## 边界

Community 是活动的公开表达层，不是产品中心。  
它不定义产品主语，也不承接与登山弱相关的泛内容表达。

## UI 原则

全部重做统一化。  
统一字号层级。  
统一 icon 规则。  
统一媒体卡片布局。  
统一操作按钮区。

---

# 6.8 Profile：个人页 / 我的记录

## 目标

突出身份、执照、记录、分享和省域归属，承接长期留存价值。

## 页面结构

用户身份头部。  
执照信息。  
基础统计。  
我的记录。  
我的分享。  
待审核记录。  
省域贡献 / 月榜入口。

## 长期方向

“我的记录”长期应演进为**私人山行档案馆**，而不是：

* 冷冰冰的数据列表
* 仅仅是发布历史
* 泛相册
* 公开炫耀型成就墙

## 档案馆表达原则

它应优先帮助用户保留少而精的内容，例如：

* 一张最能代表这次的照片
* 一个最关键的时刻
* 一句最想记住的话
* 一组最值得回看的结果数据

一层看记忆，二层看事实，三层才看传播。

# 6.9 Province Heat：省域热力

## 目标

提供长期参与感与省域归属感，而不是复杂竞技。

## 形式

轻量月榜。  
个人贡献。  
所属省份变化感。  
持续前进的轻反馈。

## 不做

不做周榜。  
不做复杂赛季。  
不做复杂奖章系统。  
不做重竞技表达。

# 6.10 FAQ：使用说明页

## 目标

降低首次使用门槛，减少误解与客服成本。

## 应覆盖的核心问题

* 怎么开始记录
* GPS 记录和照片补签有什么区别
* 为什么有的记录是待审核 / 未通过
* 什么样的记录可以发到山友圈
* 省域热力怎么算
* 如果没有这座山怎么办
* 地图和天气能力是什么、不是什麼
* 分享图怎么生成与下载
* 用户隐私和公开范围怎么理解

FAQ 作为正式产品页面处理，不应只停留在内部说明。

## 7. 关键业务规则

### 7.1 山峰准入规则

高难度山峰需要对应执照等级。  
未达到要求时，不允许直接进入正式记录流程。

### 7.2 记录有效性规则

有效记录必须服从当前有效性门槛、峰顶接近判断、短记录无效、漂移过滤等规则。  
接入更宽不等于放弃真实性边界。

### 7.3 证据规则

完整山行、登顶留证、个人归档的资格与权益应逐步形成清晰分层。  
不同分层可以对应不同公开资格、审核策略和热力贡献方式。

### 地图与天气边界

当前阶段不做重地图导航能力，也不承诺专业天气服务；但上线前必须补齐轻量地图参考能力与轻量天气接口方案。

地图在当前阶段只承担：

* 静态路线参考
* 轻量可视化参考
* 记录辅助
* 分享素材辅助

天气在当前阶段只承担：

* 轻量决策提示
* 出发前辅助判断
* 简单状态说明

当前阶段天气采用按山峰热度分层的缓存策略，不承诺所有山峰同频更新。  
热门山峰采用更高频刷新，长尾山峰允许展示较低频缓存天气，但必须展示更新时间，并明确“供出发参考”的产品边界。

### 地图与天气的实现优先级

当山峰覆盖扩展到接近 400 座时，天气能力必须采用“热度分层 + 按需刷新 + 后续区域复用”的策略，不能按“所有山峰每小时刷新一次”的思路设计。

上线前必须完成：

* QWeather 主源接入
* 服务端缓存层
* 轻量天气前端展示
* 地图静态参考图方案
* 地图 / 天气降级策略

### 7.6 内容规则

山友圈内容必须与活动绑定。  
精选攻略必须后台人工筛选。  
无精选内容时不展示该模块。

### 7.7 分享规则

每次有效活动应尽量都能产出可传播素材。  
分享入口不能过深。  
分享系统提供模板、主图、字段三个维度的有限选择权。  
分享系统不演化成专业海报编辑器。

### 7.8 海拔规则

海拔在找山、记录、分享、回看四段里都属于高优先级信息。  
不能被弱化成普通辅助字段。

### 7.9 UI 规则

高频操作统一 icon 化。  
移动端按钮区不能错行。  
弹窗、底部栏、详情操作区统一规范。  
一个页面视觉层级内最多 1 个主 CTA。

### 7.10 山峰物料规则

上线前，每座正式上线的山至少应具备：

* 山名
* 省份 / 地点
* 海拔
* 难度
* 执照要求
* 1 张主图
* 1 段简介
* 1 份基础路线参考
* 关键点位最小集
* 风险提示
* 无图兜底策略

不追求“山越多越好”，优先保证已覆盖山峰具备最低可决策完整度。

## 9. 对当前 As-Is PRD 的明确改写点

当前基线里“不做收藏体系”要继续保留。  
当前基线里“不做省域荣誉榜”要改成“做轻量省域热力月榜”。  
当前基线里“分享围绕海报编辑器展开”要改成“分享素材系统是核心能力，且提供有限字段选择权”。  
当前基线里“山友圈与真实记录绑定”要继续保留，但需要把“活动对象”和“社区内容对象”在产品文档里明确拆开。  
当前基线里详情页的主 CTA、执照限制、记录前置确认都要保留。  
当前基线里“首页仍优先指向找山”的口径，要改成“首页逐步演进为意图分流入口，Explore 仍是一号找山路径”。  
当前基线里“完整地图 SDK 与真实天气服务暂不做”的旧表述，要改成“重地图导航不做，但轻量地图 / 天气方案上线前必须补齐”。  
当前基线里未被放大的海拔，要正式升级为高优先级产品信号。  
当前基线里 Profile 更偏数据中心的表达，要逐步升级为“私人山行档案馆”的方向。

## 10. 本文档的使用说明

这份 PRD 用于定义 Peak Trekker 的目标态方向与阶段边界。  
后续所有需求讨论、Codex 指令拆分、验收标准、设计回写和技术收口，都必须优先服从以下判断：

1. 它是否服务于“我的一次真实山行”这个主语？
2. 它是在强化核心资产层，还是在制造新的分支？
3. 它是在帮助用户更真实记录、更好回看、更顺畅分享，还是在把产品带去别的赛道？
4. 它是否会与当前阶段“不做重地图导航 / 不做泛社交 / 不做复杂竞技”的边界冲突？

只要这四个问题里出现明显冲突，就不进入执行。
